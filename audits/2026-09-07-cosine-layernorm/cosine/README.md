# Cosine similarity: конечные входы, NaN-значения и градиенты

7 сентября 2026. Подтверждён ещё один отчёт по конкретной реализации:
`mlx.nn.losses.cosine_similarity_loss`. Два механизма внутри одной функции:
переполнение промежуточных произведений и неопределённая производная нормы
в неактивной ветке около нулевого вектора. Отдельные dtype и входы не считаются
независимыми находками.

| Пример | Исходный MLX | Математический результат | Локальный патч |
|---|---|---|---|
| FP16, `cosine(x,x)`, `x=[1000,-1000,1000,-1000]` | значение и градиент `NaN` | значение `1`, градиент по первому аргументу `0` | `1` и `0` |
| FP32, тот же пример с масштабом `1e20` | значение и градиент `NaN` | `1` и `0` | `1` и `0` |
| FP32, `x=0`, `y=[1e-5,2e-5,-1e-5,1e-5]`, `eps=1e-8` | значение `0`, градиент `NaN` | значение `0`, градиент `y/eps` | `0`, градиент ≈ `[1000,2000,-1000,1000]` |

Все три примера повторены в **трёх отдельных Python-процессах**, каждый на
официальных CPU и Metal 0.32.2. В `reproduction-*.json` сохранены реально
округлённые входы и результаты исходной функции и исправления.

## Проверенная математика

Документированный контракт:

`cosine(a,b) = dot(a,b) / max(norm(a) * norm(b), eps)`.

Это порог для **произведения** норм. Независимое ограничение каждой нормы через
`max(norm, eps)` меняет функцию и не используется в предлагаемом исправлении.

В большом ненулевом примере истинный ответ хорошо обусловлен и представим в
выходном dtype. FP16-квадраты и скалярное произведение переполняются; в FP32
то же происходит при достаточно больших конечных входах. Нулевой пример
показывает отдельную проблему обратного прохода: при положительном `eps`
функция в некоторой окрестности нуля равна `dot(a,b)/eps`, поэтому производная
по `a` равна `b/eps`. Неопределённая производная `sqrt` в промежуточной норме
не делает эту составную функцию недифференцируемой.

## Предложение исправления и результаты

`mlx-cosine.patch` изменяет только cosine в Python `losses.py`:

1. FP16 и BF16 промежуточные вычисления переводятся в FP32.
2. Векторы независимо масштабируются по максимальному модулю перед
   возведением в квадрат. Масштабы не участвуют в autodiff: в нормированной
   ветке они алгебраически сокращаются.
3. Проверка `eps` переносится в масштабированные координаты без произведения
   двух потенциально огромных масштабов.
4. В ограниченной через `eps` ветке меньший вектор делится на `eps` до
   умножения. Неактивные ветки защищены до опасных операций, включая `sqrt(0)`.

Сохраняются dtype результата, ось, редукции и прежняя формула для комплексных
входов и пустой оси. Патч проверен на применимость к чистому закреплённому HEAD.
Предыдущие изменения других loss-функций в этот патч не включены.

| Окончательный набор | Результат |
|---|---|
| Исходный Python HEAD + official native MLX, CPU | **62 failed / 39 passed** |
| Изменённый Python source, official core, CPU | **101 passed** |
| Изменённый Python source, official core, Metal | **101 passed** |

Набор включает сравнение значений и аналитических градиентов с mpmath
(100 десятичных знаков), FP32/FP16/BF16, три расположения батча и оси,
самоподобие, противоположные и ортогональные векторы, разные масштабы,
нулевые и малые векторы, точную семантику `eps`, три редукции, обычный
upstream-тест, `mx.compile`, целочисленный вход и ненулевые векторы при
`eps=0` и `eps=-1`. Для ненулевых FP32/BF16 градиентов используются
масштабно-чувствительные допуски, а не универсальный `atol=1e-7`.

101 — число тестовых случаев, не число независимых дефектов. Основная
граница этого ремонта — реальные векторы с конечными значениями и
представимым математическим результатом. Все возможные битовые комбинации,
крайние subnormal-режимы и производительность не исследованы. Влияние на
обучение настоящих моделей не измерялось. Upstream патч не подтверждал и
не принимал; регрессия между версиями и абсолютный приоритет не установлены.

## Версии и воспроизведение

- MLX main: `ce916dbbcaa88e433b6fd1e60a17f766d49c27fe`, сверено с GitHub в этом раунде.
- Официальные `mlx==0.32.2`, `mlx-metal==0.32.2`; это Python-патч с релизным native core, не новая нативная сборка main.

Минимальное воспроизведение на macOS Apple silicon:

```sh
python3 -m venv .venv
.venv/bin/pip install mlx==0.32.2 mlx-metal==0.32.2 numpy==2.2.6 mpmath==1.3.0 pytest==8.4.1
.venv/bin/python reproduce.py --output reproduction.json
```

Тестирование исходной реализации и патча на отдельном checkout:

```sh
git clone https://github.com/ml-explore/mlx.git mlx-audit
git -C mlx-audit checkout ce916dbbcaa88e433b6fd1e60a17f766d49c27fe
export AUDIT_MLX_SOURCE="$PWD/mlx-audit"
AUDIT_ORIGINAL=1 AUDIT_DEVICE=cpu .venv/bin/python -m pytest -q test_cosine.py
# Ожидается 62 failed / 39 passed.
git -C mlx-audit apply "$PWD/mlx-cosine.patch"
AUDIT_REPAIR=source AUDIT_DEVICE=cpu .venv/bin/python -m pytest -q test_cosine.py
AUDIT_REPAIR=source AUDIT_DEVICE=gpu .venv/bin/python -m pytest -q test_cosine.py
# Ожидается по 101 passed.
```

Минимальный `reproduce.py` автономен и не требует checkout.
`stable_cosine.py` — отдельно вызываемый вариант ремонта для реальных
непустых векторов; production-интеграция не выполнена.

## Остальной поиск и дубликаты

`probe.py` дал 244 предварительных наблюдения по нормализации, cosine,
Softmax и attention с одной разрешённой позицией. 18 флагов включают
повторы dtype/backend и требуют отдельной классификации. Его общий
абсолютный допуск не предназначен для доказательства корректности малых
градиентов. Готовый cosine-набор выше использует более строгий эталон.
LayerNorm/RMSNorm при экстремальных FP32/BF16 входах остаются отдельно
записанными кандидатами; самостоятельные готовые отчёты по ним не заявлены.

`probe_quantized.py` использует seed `7092026`, независимый декодер битовых
форматов affine/E2M1/E4M3/E8M0 и FP64-суммирование. Сравниваются сохранённые
квантованные веса, а не их приближение к исходной матрице:

- 384 вызова `quantized_matmul`: 378 укладываются в заданную оценку округления,
  6 флагов относятся к уже известному NVFP4 при `K=80`, `N=33`, `M=33/65`.
- 96 вызовов `dequantize`: 93 укладываются в допуск, 3 ошибки reshape
  принадлежат тому же ограничению CPU-упаковки NVFP4.
- Ещё 3 отдельно записанные ошибки CPU `quantize` на `(33,80)`.

В сумме 483 записи. Все 12 аномальных записей связаны с ранее описанной
семьёй [PR #3912](https://github.com/ml-explore/mlx/pull/3912) и не засчитаны
как новые. Неверные значения матричного NVFP4 могут меняться между запусками;
это не стабильная поправка к числу, а уже известная проблема обработки хвоста.
Сохранены исходный проход и последующая классификация. Первый допуск для
affine-декодирования был слишком строгим при cancellation: итоговый учитывает
округление умножения/сложения в dtype scale/bias до приведения результата.
Это не обещание корректного округления единожды из FP64 и не полная оценка
качества квантования.

По cosine точного дубликата в сохранённых поисках публичных issues/PR
(включая закрытые) не найдено. Подробности и близкие случаи — `DUPLICATES.md`.
QuantizeLinear, предыдущие BCE/logaddexp/активации и известные проблемы
полностью замаскированного attention исключены из новых находок.
